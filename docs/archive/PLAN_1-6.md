# 단계 계획 — 1-6 UI 언어

`docs/ROADMAP.md` 1-6의 상세 계획이다. 브랜치는 `1-6-ui-language`다(2026-11-28).

## 범위

`docs/DECISIONS.md` "미정"의 "UI 언어"를 정한다: 우리 화면만 한국어로 둘지, dsh 기본 화면까지 한국어 언어 팩을 등록할지, 우리 문자열을 dsh의 로케일 사전으로 옮길지. 정하기 전에 `ctx.locale`의 언어 팩 등록을 띄워서 시험했다(아래 "확인한 사실"). 정해지면 그 안을 구현하고 임시 규칙(`AGENTS.md`, `docs/CONVENTIONS.md`의 "화면 문자열은 `strings.ts` 한 모듈")을 확정하거나 고친다.

## 확인한 사실

2026-11-28에 이 단계의 워크트리에서 실험으로 봤다. **띄워 확인**은 실험용 조합 시험(dsh 0.2.2-rc.5와 헤드리스 Chromium)이고, **소스 확인**은 업스트림 `packages/client/locale/`의 소스와 README다.

**서비스**

- 브라우저 쪽 서비스 `ctx.locale`(타입은 `@deepseek-ai/dsh-client-locale/client`. 공유 모듈 표에 없으므로 값으로 가져오지 않는다). `register(ns, { zh, en, … })`(타입이 있는 형태. 한 네임스페이스의 모든 언어), `register(ns, 언어, 사전)`(언어 하나, 타입 없음), `addLanguage({ id, label, fallback })`, `setLocale(id)`, `getLocale()`, `subscribe`, `bind(ns)`, `resolveText`(**소스 확인**, 아래 실험에서 쓴 것은 **띄워 확인**).
- React 컴포넌트는 슬롯 등록에 `locale: "<ns>"`를 주면 props로 번역 함수 `t`를 받는다. 언어를 바꾸면 새로고침 없이 다시 그려진다(**띄워 확인**). 네임스페이스의 키 타입은 `LocaleNamespaceMap` 선언 병합으로 준다.
- 타입이 있는 형태는 `zh`와 `en`이 필수다. 컴파일할 때만 검사하고 런타임 검사는 없다(**띄워 확인**: 일부러 틀린 코드로 타입 검사를 돌렸다).

**활성 언어**

- 순서: 호스트에 저장된 `locale.preference` → 브라우저 언어(`navigator.languages`)와 등록된 언어의 대조 → `en`(**띄워 확인**).
- `ko`를 등록해 두면 한국어 브라우저에서는 자동으로 `ko`가 된다. 설정 → General → Language에 "한국어"가 선택지로 뜬다(**띄워 확인**).
- 고른 값은 브라우저가 아니라 home에 저장된다(프로필 `cordis.patch.yml`의 `locale` 행 `config.preference`. **띄워 확인**).
- 번들의 패치에 `locale` 행의 `preference: ko`를 넣으면 새 home이 영어 브라우저에서도 한국어로 뜬다. 뒤의 `--patch`가 같은 행을 덮는다(**띄워 확인**).

**dsh 화면의 한국어 팩**

- 우리 플러그인이 `addLanguage`로 `ko`를 더하고, dsh의 네임스페이스에 `register(ns, "ko", 사전)`으로 번역을 얹을 수 있다. 번역한 키는 한국어로, 번역하지 않은 키는 영어로 나온다(**띄워 확인**: 입력창의 전송 버튼 `aria-label`, 설정의 Language 행 제목).
- 규모: 웹 프로필이 뜬 직후 등록돼 있던 영어 사전은 **네임스페이스 63개, 키 2,928개, 영어 약 12,500낱말**이다(**띄워 확인**: 실행 중인 서비스에서 셌다. 늦게 실리는 플러그인의 사전은 빠졌을 수 있다). 큰 것은 `conversation` 392, `pluginManager` 293, `schedule.manager` 215, `chat` 207, `trajectory` 199, `settings.models` 173이다. 사전은 언어 팩 한 곳이 아니라 dsh 플러그인마다 흩어져 있다(**소스 확인**).
- 사전을 타지 않는 글이 있다: 플러그인의 제목·설명과 도구 승인 사유(`{ en, … }` 맵), 등록할 때 번역을 한 번만 읽는 문자열(예: 슬래시 명령의 설명). 이것들은 팩을 넣어도 영어로 남거나 언어를 바꿔도 그대로다(**소스 확인**).
- 빠진 키를 알려 주는 장치가 없다. 업스트림의 점검은 자기 사전만 본다. dsh 버전을 올려 키가 늘면 조용히 영어로 나온다(**소스 확인**). 점검은 우리가 시험으로 만들어야 한다.

**우리 문자열을 사전으로 옮기면**

- 패키지마다 드는 것: 키 타입 선언, `zh`·`en` 사전(타입이 요구한다), 슬롯 등록마다 `locale`, React 컴포넌트의 `t`, 개발 의존성 `@deepseek-ai/dsh-client-locale`(**띄워 확인**: 셸의 버튼 하나를 옮겨 봤다).
- 한국어만 있는 사전은 타입 없는 형태로만 된다. 그때 사용자가 English를 고르면 키 이름이 보인다(**소스 확인**).

**시험에 주는 영향**

- 조합 시험의 틀은 첫 실행 창을 영어 버튼 글자로 닫고, `chat.test.ts`는 전송·중지 버튼을 영어 `aria-label`로 가른다. 지금 시험이 영어인 것은 헤드리스 브라우저의 언어가 `en-US`라서다.
- dsh 화면의 한국어 팩이 그 글자들을 번역하고 한국어가 활성이면 시험이 깨진다. 시험이 `locale` 행 `preference: en` 패치를 얹어 영어를 강제하면 된다(패치가 이기는 것은 **띄워 확인**).

**LLM이 읽는 글**

- 로케일 서비스는 화면 계층이다. 시스템 프롬프트와 도구 설명은 활성 언어를 쓰지 않는다(**소스 확인**).

## 결과

- 코드는 바뀌지 않았다. 실험에 쓴 코드(셸의 언어 팩·사전 등록, 버튼 하나의 `t` 전환, 실험용 조합 시험 셋)는 지웠다.
- `docs/DSH.md` "그릴 재료"의 "언어"에 결정과 확인한 사실을 적었다. "확인하지 못한 것"에서 한국어 언어 팩 등록과 슬롯 등록의 `locale` 칸을 지웠다.
- `AGENTS.md`와 `docs/CONVENTIONS.md`의 임시 규칙을 확정된 규칙으로 고쳤다.
- `docs/DECISIONS.md`: "확정"에 두 줄을 더하고 "미정"의 "UI 언어"와 "전제"의 임시 규칙을 지웠다.
- `docs/ARCHITECTURE.md` "설계 과제"에서 UI 언어를 지웠다.

### 실험에서 돌린 것

셸의 브라우저 절반에 실험용 모듈을 임시로 더하고(`inject`에 `locale`), 실험용 조합 시험 셋으로 봤다.

- 언어 팩과 우리 사전: `addLanguage({ id: "ko", label: "한국어", fallback: "en" })`, `register("conversation", "ko", { "input.send": … })`, `register("cs.shell", { zh, en, ko })`, 슬롯 등록의 `locale: "cs.shell"`. 헤드리스 브라우저에서 `setLocale("ko")` 뒤에 전송 버튼의 `aria-label`과 우리 버튼의 글자가 바뀌는 것, 번역하지 않은 키가 영어로 남는 것, 설정의 Language 선택지에 "한국어"가 뜨는 것을 봤다.
- 기본 언어: 번들 자리의 `locale` 행 `preference: ko`로 영어 브라우저가 한국어로 뜨는 것, 브라우저 언어가 `ko-KR`이면 저장 없이 `ko`가 되는 것, 고른 값이 프로필의 패치 파일에 쓰이는 것.
- 덮기: `ko` 행 뒤에 `preference: en` 패치를 주면 영어로 뜨는 것(시험이 영어를 강제하는 길).
- 크기: 실행 중인 로케일 서비스의 사전을 세었다.

### 확인하지 못한 것

- 전체 언어 팩을 넣고 첫 실행 창과 채팅 시험을 돌리는 것(깨진다는 것은 부분 팩과 소스에서 낸 판단이다).
- 한국어만 있는 사전(타입 없는 등록)은 소스로만 봤다.
- 호스트가 내는 오류 글의 언어, 늦게 실리는 플러그인의 사전.
