# 단계 계획 — 2-1 계약 ①: 카탈로그

`docs/ROADMAP.md` 2-1의 상세 계획이다. 브랜치는 `2-1-catalog-contract`다(2026-11-28).

## 범위

생성 프로바이더가 꽂히는 자리를 정한다. 계획 2의 기능 컴포넌트(2-3)와 계획 4의 Comfy 연결(4-2)이 이 계약만 보고 따로 만들어지게 하는 것이 목적이다.

- 계약 타입과 카탈로그 서비스를 가진 패키지 `@cs/catalog`(서비스 `ctx.csCatalog`).
- 가짜 생성 프로바이더로 계약을 끝까지 도는 시험.
- 화면용 API에 카탈로그 목록 라우트와 변경 이벤트.

범위 밖: 실제 Comfy 생성 프로바이더와 실행기(4-2), 생성·워크플로 기능 컴포넌트(2-3), 서버 등록과 자격 증명(4-1), 카탈로그를 읽는 에이전트 도구(생성 기능 컴포넌트와 함께 2-3).

## 설계에 쓴 사실

- **DreamVerse의 카탈로그**(`@dv/models`, **소스 확인(DreamVerse)**, 2026-11-28): 서비스 `dvModels`에 프로바이더 플러그인이 항목을 등록한다(`register(entry)` → 정리 함수). 항목의 열쇠는 `(modality, task, provider, model)`이고, 항목은 `description`, `facts()`, `schema()`, `validateGenerationRequest(request)`, `render(request, signal)`을 가진다. 요청·결과의 타입은 "프리미티브"마다의 표(`PrimitiveTypes`)에서 오고, 새 프리미티브는 선언 병합으로 더한다. 소비자는 `whileServing(tasks, start)`로 그 작업을 맡는 항목이 있는 동안만 자기 연산을 등록한다. `onChanged(listener)`가 등록·해제를 알린다.
- **DreamVerse의 생성 틀**(`@dv/generation`): 검증(`validateGenerationRequest`)을 에이전트 도구 호출의 `prepareToolCall`에서 한 번(기록을 쓰기 전), `execute` 안에서 한 번 더 부른다.
- **기존 앱의 `ComfyBackend`**(`comfy-studio`의 `src/lib/comfy/backend.ts`, **소스 확인**): 서버 종류 넷(local, cloud, runpod, modal)을 가리는 인터페이스다. `systemStats`, `objectInfo`, `listNodeClasses`, `queuePrompt`, `result`, `cancel`, `uploadImage`, `view`와 선택 메서드 `openSocket`, `releaseOutputs`, `listHistory`, `listModels`, `modelMetadata`. 선택 메서드는 서버 종류에 따라 있거나 없다.
- **프로젝트 계층의 실행 흐름**(`packages/project/CONTRACTS.md`, **띄워 확인**): 파라미터 검증 → 잠금 안에서 입력을 풀고 연산의 `precondition`을 부른다(여기서 거절되면 기록이 없다. 잠금 안이라 빨라야 한다) → `pending` 기록 추가 → 잠금 밖에서 `execute` → 갱신 줄. 에이전트 도구 호출은 그 전에 `prepareToolCall`을 지난다. `execute`가 받는 것은 기록, 입력, 상태, 임시 폴더(`scratchDir`), 중지 신호, `importAsset`이다. 실행 도중에 기록에 값을 덧붙이는 길은 없다. **재시작하면 끝나지 않은 기록은 `cancelled`가 된다**("ends unfinished records at start").
- **기존 앱의 실행 규칙**(`docs/LEGACY.md` "유지할 도메인 규칙"): 완료 판정은 폴링이 기준이다. 취소의 결과는 셋이다(`canceled`, `running`, `finished`). 이미지 입력은 참조로 받아 실행 직전에 서버의 input 폴더로 복사한다. `/prompt` 검증 실패는 기록을 남기지 않는다. 실행 추적, 결과 수집, 취소 판정은 한 곳에서 한다.

## 사용자가 정할 것

`docs/DECISIONS.md` "미정"의 "카탈로그 계약의 모양"이었다. 아래 안을 보였고 **사용자가 셋 모두 권한 안을 골랐다(2026-11-28)**: 항목은 서버 하나, 요청은 완성된 그래프이고 결과는 이벤트 스트림, 검증은 기록 전에 하고 서버의 거절은 실행으로 세지 않는다. 질문 번호는 구현 전의 `docs/ARCHITECTURE.md` "카탈로그 계약"에 있던 것이다.

### 1. 카탈로그 항목 하나는 무엇인가 (질문 1)

| 안 | 항목 | 열쇠의 예 | 장점 | 단점 |
| --- | --- | --- | --- | --- |
| **서버 하나(권함)** | 등록된 ComfyUI 서버 하나 | `graph / comfy / <서버 id>` | 카탈로그가 "어디서 돌릴 수 있는가"의 목록이 된다. 워크플로(템플릿)는 워크플로 기능 컴포넌트의 데이터로 남아 주인이 하나다. 서버를 더하고 빼는 것이 항목의 등록·해제와 같다 | 에이전트가 "무엇으로 만들지"를 고르려면 카탈로그(서버)와 워크플로 목록 둘을 본다 |
| 서버 × 워크플로 | 어느 서버에서 어느 템플릿을 돌릴 수 있다는 짝 | `image / comfy / <서버 id> / <템플릿 id>` | DreamVerse의 "모델 × 작업"과 가장 닮았다. 요청이 필드 값만으로 줄어든다 | 템플릿은 사용자가 수시로 만드는 데이터다. 프로바이더가 워크플로 기능 컴포넌트의 데이터를 알아야 해서 의존이 거꾸로 선다. 항목 수가 서버 수 × 템플릿 수다 |
| 서버 종류 하나 | local, cloud, runpod, modal 구현 넷 | `graph / comfy-local` | 항목이 고정이다 | 대상 서버가 요청의 필드가 되어, 서버마다 다른 사실(노드 카탈로그, 모델 파일)을 항목이 답하지 못한다 |

### 2. 요청과 결과의 모양 (질문 2, 3)

| 안 | 요청 | 결과 | 장점 | 단점 |
| --- | --- | --- | --- | --- |
| **완성된 그래프 + 이벤트 스트림(권함)** | 실제로 보낼 API 형식 그래프 전체(패치와 필드 값이 이미 적용된 것)와, 미디어 입력을 가리키는 에셋 참조 목록 | 이벤트의 흐름: `queued`(서버가 받음. 실제로 보낸 그래프가 실린다) → `progress`* → `output`*(파일 하나씩) → `done` | 템플릿·패치·필드를 그래프로 만드는 일은 기능 컴포넌트가 연동 라이브러리의 순수 함수로 한다. 프로바이더는 워크플로를 몰라도 된다. 기록에 실제로 보낸 그래프가 남는다. 진행률과 여러 출력이 한 흐름으로 온다 | 요청이 크다(그래프 전체). 기록의 파라미터에는 템플릿 참조·패치·필드 값을, 보고에는 보낸 그래프를 따로 남긴다 |
| 템플릿 참조 + 패치 + 필드 값 | 템플릿 id, 그래프 패치, 필드 값 | 위와 같다 | 요청이 작고 사용자가 한 말과 같다 | 프로바이더가 템플릿을 읽어 그래프를 만들어야 한다(의존이 거꾸로 선다). 가짜 프로바이더도 그 일을 해야 한다 |
| 완성된 그래프 + 출력 파일 목록 | 권하는 안과 같다 | 끝난 뒤의 출력 파일 목록 하나(진행률은 콜백) | 단순하다 | 진행률·취소·이어받기가 계약 밖으로 흩어진다. 출력이 많은 실행에서 하나씩 저장하지 못한다 |

권하는 안에서 **진행률·완료 판정·출력 수집·취소 판정은 프로바이더가 한다**(기존 규칙 "한 곳에서 한다"). 기능 컴포넌트는 흐름을 읽어 출력을 에셋으로 저장하고 기록의 보고를 만든다. 취소는 중지 신호 하나다: 프로바이더가 서버에 취소를 보내고, 서버가 이미 끝냈으면(`finished`) 흐름을 끝까지 내보내 결과를 살리고, 아니면 흐름을 중지로 끝낸다.

### 3. `/prompt` 검증 실패와 기록 (질문 6)

프로젝트 계층은 `pending` 기록을 쓴 뒤에 `execute`를 부른다. 서버 제출은 `execute` 안이라, 서버가 그래프를 거절하면 이미 기록이 있다.

| 안 | 하는 일 | 기존 규칙과의 관계 | 단점 |
| --- | --- | --- | --- |
| **기록 전 검증 + 거절은 실행으로 세지 않는다(권함)** | 프로바이더의 `validate`(큐에 넣지 않는 검증: 그래프 구조, 서버의 노드 카탈로그 대조, 입력 에셋)를 기록을 쓰기 전에 부른다. 여기서 걸리면 기록이 없다. 그것을 통과하고도 서버가 제출을 거절하면 기록은 `failed`로 남되 보고에 "큐에 가지 않았다"가 적혀, 생성 목록과 배치가 실행으로 세지 않는다 | 대부분의 검증 실패는 기록을 남기지 않는다. 드문 서버 거절은 히스토리에 실패한 단계 하나로 남지만 실행으로 치지 않는다 | 기록 파일에 줄이 남는 경우가 있다(규칙을 글자 그대로는 지키지 못한다) |
| 제출을 기록 전에 | 기능 컴포넌트가 기록을 쓰기 전에 서버에 제출하고, 받은 실행 id를 기록에 싣는다 | 글자 그대로 지킨다 | 제출과 기록 사이에 실패하면 서버에 주인 없는 실행이 남는다. 끝나지 않은 기록을 입력으로 받아 예약되는 호출(스케줄러)은 기록이 먼저 있어야 해서 이 길로 못 간다. 프로젝트 계층의 흐름을 우회한다 |
| 규칙을 바꾼다 | 서버 거절도 실패한 실행으로 센다 | 규칙을 버린다(RunPod은 지금도 거절을 실패한 작업으로 뒤늦게 안다) | 잘못 만든 그래프가 생성 목록에 실패로 쌓인다 |

## 고른 것

Claude가 고른 기본값이다. 사용자가 고른 세 안 아래의 세부이고, `docs/DECISIONS.md` "전제"에 적는다.

| 무엇 | 고른 것 | 이유 | 뒤집으면 |
| --- | --- | --- | --- |
| 패키지 | `packages/catalog`, `@cs/catalog`. 호스트 절반만 있다. 서비스는 `ctx.csCatalog`, 번들 행 id는 `cs-catalog` | `docs/ARCHITECTURE.md` "패키지 구성(가칭)"의 이름이다 | 이름만 바꾼다 |
| 틀 | DreamVerse의 것을 쓴다: 프리미티브마다의 타입 표(`PrimitiveTypes`)와 선언 병합, `register`·`get`·`list`·`onChanged`·`whileServing`. 지금 선언하는 프리미티브는 `graph` 하나다 | 그래프가 아닌 생성(프롬프트 기반 API 등)이 생기면 프리미티브를 더하면 된다. 옮겨 오는 코드는 틀 부분뿐이다(약 150줄) | 프리미티브 표를 없애고 `graph` 전용으로 줄인다 |
| 서버 조회(질문 4) | 항목의 **선택 메서드**로 둔다: 노드 카탈로그, 모델 파일 목록과 메타데이터, 서버의 실행 기록. 있으면 되는 서버, 없으면 안 되는 서버다. 가벼운 사실(종류, 이름, 되는 것)은 `facts()` | 기능 컴포넌트가 프로바이더 플러그인을 직접 주입하지 않고 카탈로그만 본다(의존 방향). 기존 `ComfyBackend`의 선택 메서드와 같은 방식이다 | 별도 서비스로 빼면 기능 컴포넌트 → 프로바이더 의존이 생긴다 |
| `ComfyBackend`(질문 5) | 카탈로그 아래의 내부 인터페이스로 그대로 둔다. 프로바이더(4-2)가 항목 하나를 `ComfyBackend` 하나 위에 구현한다. 계약 패키지는 연동 라이브러리에 의존하지 않는다(그래프 타입은 구조만 맞춘 자체 선언) | 서버 종류 넷이 이미 이 인터페이스로 돌고 있다. 계약이 연동 라이브러리를 몰라야 2-1과 4-0이 서로를 기다리지 않는다 | — |
| 재시작 후 이어받기 | 계약에 `resume`(이미 받아들여진 실행 id로 같은 흐름을 다시 여는 선택 메서드)을 둔다. 그것을 재시작 때 쓰는 것은 정하지 않는다 | 프로젝트 계층은 재시작 때 끝나지 않은 기록을 `cancelled`로 끝낸다. 이어받으려면 프로젝트 계층을 고치거나 실행 id를 기록 밖에 둬야 한다. 생성 실행기를 만드는 4-2의 설계 과제다 | `docs/ARCHITECTURE.md` "설계 과제"에 적는다 |
| 출력 파일을 넘기는 법 | 프로바이더가 호출자가 준 폴더(연산의 `scratchDir`)에 파일로 쓰고 이벤트에는 경로를 싣는다 | 영상은 수백 MB다(기존 상한 512MB). 메모리에 올리지 않고 `importAsset({ path })`로 넘긴다 | 바이트를 이벤트에 싣는다 |
| 화면용 API | `GET /api/cs/catalog`(항목 목록과 `facts`)와 스트림의 `catalog` 이벤트를 `@cs/api`에 더한다. 카탈로그가 없으면 빈 목록이다 | 설정 화면(3-5)과 실행 폼(3-3)이 서버 목록을 읽는다. DreamVerse의 `/api/dv/models`·`models` 이벤트에 해당한다 | 라우트를 뺀다 |
| 미디어 입력을 읽는 길 | 요청은 에셋 id를 싣고, 프로바이더는 `run`의 옵션으로 받은 에셋 리더(`assets.get`, `assets.read`)로 읽는다. 부르는 쪽이 프로젝트 계층의 `csProject.assets()`를 넘긴다. 그 리더에 `read`를 더했다(읽기만) | 프로바이더가 프로젝트 계층의 서비스를 주입하지 않아도 되고, 시험에서 가짜 프로바이더가 서비스 없이 돈다. DreamVerse는 프로바이더가 에셋 풀 서비스를 직접 읽는다 | 옵션에서 빼고 프로바이더가 `csProject`를 주입한다 |
| 거절을 기록에 남기는 법 | 프로바이더는 `RequestRejected`(문제 목록)로 거절한다. 부르는 연산이 그것을 받아 기록의 실패 코드를 `not_queued`(`NOT_QUEUED`)로 남긴다. 그러려고 프로젝트 계층에 `OperationFailure(code, message)`를 더했다: `execute`가 이것을 던지면 기록의 `error.code`가 `operation_failed` 대신 그 코드가 된다 | 실패한 기록은 보고(`report`)를 싣지 못하고 오류 코드와 메시지만 싣는다. 코드가 있어야 리듀서와 화면이 메시지를 읽지 않고 가려낸다 | 메시지의 머리말로 가린다(약하다) |
| `validate`를 부르는 자리 | 연산의 `precondition`이다(에이전트와 화면 둘 다 지나고, 기록을 쓰기 전이다). 프로젝트 잠금 안이라 `validate`는 프로바이더가 이미 가진 것(캐시한 노드 카탈로그)으로 빨리 답해야 한다고 계약에 적었다. 이 시점에는 입력이 아직 풀리지 않아 미디어 입력은 검증에 들어가지 않는다(에셋이 있는지는 프로젝트 계층이 본다) | DreamVerse는 에이전트 도구 호출에서만 미리 검증한다(`prepareToolCall`). 화면에서 부른 호출도 기록 전에 걸러야 한다 | `prepareToolCall`로 옮기고 화면은 사전 확인 라우트로 거른다 |
| 열쇠와 듣는 쪽 | 열쇠의 세 부분은 어떤 글자든 받고 서로 섞이지 않는다(`a/b`+`c`와 `a`+`b/c`는 다른 항목). 프로바이더와 대상이 비면 거절한다. `onChanged`의 듣는 쪽이 던져도 등록과 다른 듣는 쪽은 그대로 간다(로그만 남긴다) | 서버 id의 모양은 4-1이 정한다. 소비자 하나의 오류가 프로바이더의 등록을 깨면 안 된다 | — |
| 에이전트 도구 | 카탈로그를 읽는 에이전트 도구(DreamVerse의 `dv_models_list`·`dv_models_get`)는 만들지 않는다 | 무엇을 보여 줄지는 생성 기능 컴포넌트(2-3)가 워크플로와 함께 정한다 | 2-3에서 더한다 |

## 계약

정해진 모양이다. 타입은 `packages/catalog/src/types.ts`, 서비스는 `packages/catalog/src/index.ts`에 있고, 요약은 `docs/ARCHITECTURE.md` "카탈로그 계약"에 있다.

- **열쇠**: `{ primitive, provider, target }`. 지금 프리미티브는 `graph` 하나이고, `target`은 프로바이더가 서버에 붙인 id다.
- **항목**(`CatalogEntry<P>`): `description`, `facts()`, `validate(request)`, `run(request, { dir, assets, signal })`, 선택 `resume(run, options)`. `graph` 항목은 선택 조회 `nodeCatalog()`, `listModelFiles(folder)`, `modelFileMetadata(folder, file)`, `listRuns(limit)`을 더 가질 수 있다.
- **요청**(`GraphRequest`): `graph`(보낼 그래프 전체)와 `media`(`{ node, input, asset }`의 목록).
- **이벤트**(`GraphRunEvent`): `queued{run, graph}` → `progress{node, value, max}`* → `output{node, name, mime, path, preview}`* → `done`. 실패는 순회가 거절된다. 서버가 그래프를 실행하지 않고 거절하면 `RequestRejected`로 거절된다(제출에 바로 답하는 서버는 이벤트 없이, 작업 큐는 `queued` 뒤에).
- **중지**: `signal`이 중지되면 프로바이더가 서버에 취소를 보낸다. 서버가 이미 끝냈으면 출력과 `done`까지 내고, 아니면 `Error`로 거절한다.
- **순회의 끝**: `done` 뒤에 순회가 끝나고 그 뒤로는 거절하지 않는다. 부르는 쪽이 일찍 그만두면 프로바이더가 실행을 취소한다. 어떻게 끝나든 프로바이더는 쥔 것을 놓고 `dir`에 더 쓰지 않는다.
- **검증**: `validate(draft, signal?)`는 입력이 풀리기 전의 요청(그래프와 미디어 입력의 자리)을 받는다.
- **서비스**(`ctx.csCatalog`): `register(entry)`, `get(key)`, `list(filter?)`, `onChanged(listener)`, `whileServing(primitives, start)`, `summary()`.

## 시험

단위 시험(`packages/catalog/src/*.test.ts`):

- 서비스: 등록과 해제, 같은 열쇠 거절, `list`의 필터, `onChanged`, `whileServing`(항목이 생기면 시작하고 마지막 항목이 빠지면 멈춘다), `summary`가 `facts()` 거절을 견딘다.
- 가짜 생성 프로바이더(`src/testing/fake-provider.ts`, `@cs/catalog/testing/fake-provider`로 내보낸다): 그래프를 받아 `queued` → `progress` → `output`(작은 PNG) → `done`을 내는 항목. 검증 실패, 제출 거절(`RequestRejected`), 실행 중 실패, 중지(취소됨 / 이미 끝남)를 설정으로 고른다.
- **계약을 끝까지 도는 시험**: 실제 `CsProject`에 시험용 연산을 등록하고, 그 연산의 `execute`가 카탈로그에서 가짜 항목을 찾아 `run`의 흐름을 읽고 출력을 `importAsset`으로 저장하고 보낸 그래프를 보고에 남긴다. 3번 질문의 답에 따라 검증 실패가 기록을 남기지 않는 것과 제출 거절이 기록에 남는 모양을 본다. 이 시험이 2-3과 4-2가 따를 본이다.

조합 시험(`tests/integration/catalog.test.ts`): 번들의 행으로 서비스가 올라오고, 픽스처 플러그인이 등록한 가짜 항목이 `GET /api/cs/catalog`에 보이고, 등록·해제 때 스트림에 `catalog` 이벤트가 오고, 연산이 열쇠로 항목을 찾아 실행의 흐름을 끝까지 읽는다. 이 프로필에는 아직 에셋 저장소가 없어 출력 파일을 에셋으로 넣는 것은 단위 시험(끝까지 도는 시험)에서 본다.

### 계획과 달라진 것

| 계획 | 실제 | 이유 |
| --- | --- | --- |
| 요청의 미디어 입력을 프로바이더가 어떻게 읽는지 적지 않았다 | `run`의 옵션에 에셋 리더(`assets`)를 넣었다. 프로젝트 계층의 리더에 `read`를 더했다 | 프로바이더가 프로젝트 계층의 서비스를 주입하지 않게 했다 |
| 거절한 기록은 "보고에" 큐에 가지 않았다고 적는다 | 기록의 실패 코드를 `not_queued`로 남긴다. 프로젝트 계층에 `OperationFailure`를 더했다 | 실패한 기록은 보고를 싣지 못한다. 오류 코드와 메시지만 싣는다 |
| `validate(request)` | `validate(draft, signal?)`. `draft`는 그래프와 미디어 입력의 자리다 | 기록 전(`precondition`)에는 입력이 에셋으로 풀리지 않았다. 그 자리의 자리표시자를 프로바이더가 판단하면 미디어 입력이 있는 호출이 전부 거절된다(리뷰) |
| `RequestRejected`는 `queued` 전에만 | `queued` 뒤에도 된다 | 작업 큐는 제출이 늘 성공하고 그래프의 거절을 나중에 알려 준다. 그것도 실행으로 세지 않아야 한다(리뷰) |
| 출력을 받는 대로 에셋에 넣는다 | `done` 뒤에 넣는다 | 중간에 실패한 실행이 기록 없는 에셋을 남긴다(리뷰) |
| 항목의 선택 메서드 이름을 요약에 싣는 것은 계획에 없었다 | `summary()`의 `abilities` | 화면이 서버마다 되는 것을 알아야 한다(준비 점검, 실행 기록 가져오기) |

구현과 독립된 리뷰(상위 등급)를 한 번 받았다. 계약을 실제 ComfyUI 실행과 서버리스 실행에 대어 보고, 의심 가는 곳은 시험을 써서 재현했다.

| 지적 | 처리 |
| --- | --- |
| P1 순회가 어떻게 끝나는지 계약이 말하지 않는다(부르는 쪽이 일찍 그만둘 때, 끝난 뒤의 쓰기, 출력 경로) | 계약에 적고 가짜 프로바이더가 지키게 했다: 일찍 그만두면 취소, 끝난 뒤 `dir`에 쓰지 않음, 출력 경로는 `dir` 바로 아래의 겹치지 않는 파일. 시험 넷을 더했다 |
