# 2-3d 단계 계획 — 생성

2-3의 넷째 갈래다. 워크플로를 카탈로그의 `graph` 항목으로 실행하는 기능 컴포넌트 `@cs/generation`을 만든다. 2-3 전체에 걸리는 결정은 `docs/archive/PLAN_2-3a.md`에 있다.

- 실행은 카탈로그 계약(`@cs/catalog`)의 `graph` 항목이 한다. 본은 `packages/catalog/src/contract.test.ts`다. 등록된 생성 프로바이더는 아직 없으므로(4-2) 시험은 가짜 생성 프로바이더(`@cs/catalog/testing/fake-provider`)로 한다.
- 그래프를 만드는 일(템플릿 → 패치 → 필드 값)은 워크플로 기능 컴포넌트의 서비스와 순수 함수(`ctx.csWorkflow.resolve`, `@cs/workflow/files`)와 연동 라이브러리 `@cs/comfy`로 한다.
- 연산, 리듀서, 에이전트가 읽는 글은 새로 쓴다. 기존 앱의 동작이 본이고 코드는 옮기지 않는다.

## 프로젝트 계층에 더하는 것

생성에 필요한 것 셋이다. 프로젝트 계층의 계약이 바뀌므로 먼저 만든다(수명과 동시성이 걸려 상위 등급이 맡는다).

1. **호출 때 정해지는 `agent`.** `OperationSpec.agent`가 값 대신 함수 `(state) => AgentCall`일 수 있다. 실행기, 도구, 히스토리 이동 가드가 그때의 상태로 값을 구한다(`agentCallOf(spec, state)`). 함수인 연산은 늘 도구가 있고, 도구 설명의 끝에 "프로젝트 설정에 따라 실행되거나 제안만 남는다. 결과의 `status`가 말해 준다"는 문장이 붙는다. 화면용 API의 연산 선언은 `agent: "by_state"`로 싣는다.
2. **늘 예약되는 연산.** `OperationSpec.background: true`인 연산은 `run`이 기록을 `pending`으로 쓰고 바로 돌아온다(`after: []`와 같다). 스케줄러가 자원 한도 안에서 실행한다. 화면의 요청, 에이전트의 도구 호출, 제안의 승인이 모두 실행이 끝나기를 기다리지 않는다. 에이전트는 `cs_proj_wait`로 기다린다.
3. **기록 멈추기.** `ctx.csProject.cancel(project, record, origin)`: 끝나지 않은 기록을 멈춘다. 대기열에 있으면 빼고 `cancelled`로 끝내고, 실행 중이면 그 실행의 신호를 끊는다(`error.code: "stopped"`). 끝난 기록은 그대로 돌려준다. 사용자만 한다(에이전트 origin은 `agent_not_allowed`). 화면용 API는 `POST /api/cs/record/cancel {project, record}`다.

## 패키지

`@cs/generation`(`packages/generation`), 서비스 `ctx.csGeneration`, 번들 행 `cs-generation`, 컴포넌트 열쇠 `gen`. `csProject`, `csWorkflow`, `csCatalog`를 주입받는다. `gen.run`은 카탈로그에 `graph` 항목이 있는 동안만 등록된다(`csCatalog.whileServing(["graph"], …)`). 나머지 연산은 늘 있다.

## 상태 조각

`ComponentStates.gen`은 설정 하나다. 실행의 목록은 조각에 두지 않는다: `gen.run` 기록과 그 `report`가 이미 상태의 `proj.records`에 있고, 화면과 읽기 연산이 거기서 읽는다.

```ts
export interface GenSlice {
  settings: {
    /** Whether an agent's call of gen.run runs at once (true) or writes a proposal (false, the default). */
    agent_run: boolean;
  };
}
```

## 연산

전부 `component: "gen"`, `version: "1"`이다.

| 연산 | `agent` | 입력 | 파라미터 | 하는 일 |
| --- | --- | --- | --- | --- |
| `gen.run` | 설정에 따라 `run`이나 `propose`(기본) | `media`(여럿) | `workflow`, `values?`, `ops?`, `media_fields?`, `target?`, `count?`(1~4, 기본 1), `label?` | 워크플로를 실행한다. 요청 하나가 배치 하나이고 기록 하나다. `resource: "gpu"`, `background: true` |
| `gen.settings` | `none` | — | `agent_run`(불리언) | 에이전트가 생성을 바로 실행해도 되는지를 정한다. 히스토리 밖이다 |
| `gen.targets` | 읽기 | — | — | 실행할 수 있는 자리(카탈로그의 `graph` 항목): 열쇠, 이름, 종류, 설명, 닿지 않으면 그 이유 |
| `gen.list` | 읽기 | — | `status?`, `workflow?`, `limit?`(1~50, 기본 10) | 최근 배치: id, 라벨, 워크플로, 상태, 실행 수, 출력 수 |
| `gen.get` | 읽기 | — | `record` | 배치 하나: 실행마다의 시드·출력(id, 주소, 검토 상태는 에셋 조각이 있으면)·오류, 쓴 값 |

`gen.run`:

- **그래프를 만드는 순서**: 워크플로의 그래프(템플릿) → `ops`(그래프 패치) → 필드 값(`values`. 패치가 값을 준 필드는 그 값이 기본값이다: `rebaseParams`) → 실행마다 시드. 템플릿은 바뀌지 않는다. 패치한 그래프를 남기려면 `workflow.save_variant`다.
- **미디어 입력**: `media_fields[i]`(필드 id `<노드>.<입력>`)에 입력 `media`의 i번째 에셋이 들어간다. 프로바이더가 실행 직전에 서버에 올리고 그 이름을 그래프에 써넣는다(카탈로그 계약). 미디어 필드에 에셋을 주지 않으면 템플릿에 적힌 서버의 파일 이름이 그대로 간다.
- **시드**: 종류가 `seed`인 필드는 값을 주지 않으면 실행마다 새로 뽑는다. 값을 주면 첫 실행이 그 값을 쓰고 둘째부터는 새로 뽑는다.
- **실행 자리**: 파라미터의 `target`, 없으면 워크플로의 기본 자리, 없으면 카탈로그의 `graph` 항목이 하나뿐일 때 그것이다. 정해지지 않으면 `gen.targets`로 고르라고 알리며 거절한다.
- `precondition`(기록 전 거절): 워크플로 id, 패치(적용과 구조 검사), 값(종류에 맞는지: `coerceParamValue`. 없는 필드 id는 거절), `media_fields`와 `media` 입력의 수가 같고 각각 그래프의 리터럴 입력을 가리키는지, 미디어 필드의 종류와 에셋의 종류(이미지·오디오·영상)가 맞는지, `count`, `label`(100자), 실행 자리가 있는지, 그 항목의 `validate`가 문제를 내지 않는지.
- `execute`: `count`번 차례로 `entry.run`을 돈다. 실행마다 임시 폴더를 따로 준다. 출력은 그 실행의 `done` 뒤에 에셋으로 들인다. 기록의 `outputs`는 모든 실행의 출력이다(에셋 리듀서가 검토 대기로 들인다).
- **끝나는 모양**: 하나라도 끝난 실행이 있으면 기록은 `done`이고 실패한 실행은 `report.runs[i].error`에 남는다. 하나도 끝나지 못했으면 기록은 `failed`다: 전부 서버가 받지 않은 것이면 코드 `not_queued`(카탈로그의 `NOT_QUEUED`), 아니면 첫 실패의 문장이다. 멈춤(신호)이 오면 남은 실행을 하지 않는다: 끝난 실행이 있으면 `done`(`report.stopped: true`), 없으면 `cancelled`다.
- `report`(`GenRunReport`): 워크플로 id와 이름, 실행 자리, 준비한 그래프(시드를 넣기 전)의 블롭 id, 쓴 값, 실행마다 `{ run, seeds, outputs, error? }`.

에이전트 요약(`agentSummary`): `generation`(`{ agent_may_run, unfinished, recent }`. `recent`는 마지막 다섯 배치의 `{ id, label, status, outputs }`).

확인한 것:

- `pnpm check` 통과(단위 시험 1152개. 이 갈래의 것은 `packages/generation` 69개와 프로젝트 계층·화면용 API에 더한 것).
- `pnpm test:integration` 통과(29개). 새 시험 `tests/integration/generation.test.ts`가 가짜 생성 프로바이더를 등록한 실제 dsh에서 본다: 워크플로를 만든다 → 가짜 LLM이 `cs_gen_run`을 부른다 → 제안으로 남고 아무것도 돌지 않는다 → 승인하면 답이 바로 오고(기록은 `pending`) 배경에서 실행이 끝난다 → 두 실행의 출력이 에셋 조각에 검토 대기로 뜬다 → 끝난 기록을 멈추면 그대로 돌려준다 → 사용자가 `gen.settings`로 켠다 → 다음 호출은 제안 없이 실행된다. 모델이 받는 도구에 `cs_gen_settings`가 없다.
- 실제 ComfyUI 서버와 실제 모델로는 돌려 보지 않았다(**미확인**. 생성 프로바이더는 4-2다).

구현하며 더 정한 것(Claude가 고른 기본값):

- **배경 실행을 에이전트가 아는 길.** 도구 결과는 `pending`으로 바로 온다. 실행이 끝나면 프로젝트 갱신 메시지(`Project updates since your last step`)에 "네 호출이 끝났다"가 실린다. 실행이 금방 끝나면 같은 턴의 다음 요청에 실린다(조합 시험에서 봤다). 오래 걸리면 `cs_proj_wait`로 기다린다.
- **멈춘 배치.** 멈춤이 오면 시작하지 않은 실행은 시작하지 않는다. 돌던 실행은 서버가 이미 끝냈으면 끝난 것으로, 아니면 `stopped` 오류로 남는다. 끝난 실행이 하나라도 있으면 기록은 `done`(`report.stopped: true`), 없으면 `cancelled`다.
- **실패한 기록에는 `report`가 없다.** 프로젝트 계층의 실패에는 코드와 문장만 실린다. 하나도 끝나지 못한 배치는 첫 실패의 문장만 남고 실행마다의 오류는 남지 않는다. 일부만 끝난 배치는 `done`이라 `report.runs`에 실행마다의 오류가 있다.
- **시드.** 값을 준 시드와 패치가 값을 준 시드는 첫 실행만 그 값을 쓴다. 그 밖의 시드 필드는 첫 실행부터 새로 뽑는다.
- **미디어 필드**는 값(`values`)으로 줄 수 없고 에셋으로만 준다. `media_fields`가 가리키는 것은 미디어 종류의 필드이거나 글 리터럴 입력이어야 한다.
- **실행 자리**: `target`, 워크플로의 기본 자리, 하나뿐인 항목의 순서로 찾고, 정해지지 않으면 `cs_gen_targets`를 부르라고 알리며 거절한다.
- `gen.run`의 도구 결과는 파라미터를 되풀이하지 않는다(`omitParamsFromResult`).
- **프로젝트 계층**: 함수인 `agent`는 도구에서 한 번, `run`의 잠금 안에서 한 번 묻는다. 그 사이에 설정이 바뀌면 `run`이 거절한다(제안으로 바꾸지 않는다). 예약(`enqueue`)은 `run`의 잠금 안에서 한다(멈추기가 기록을 늘 대기열·시작 전·실행 중 가운데 하나로 본다). 멈춘 기록의 오류는 `{ code: "stopped", message: "Stopped by the user." }`다. 멈추기는 실행 중인 기록이 끝날 때까지 기다린 뒤 답한다(잠금은 쥐지 않는다).

| `media_fields`에 `constructor.image` 같은 이름을 주면 `TypeError`가 새어 나간다(화면용 API는 500) | 그래프와 입력을 자기 열쇠로만 찾는다 |
| 새로 뽑는 시드가 필드의 `max`를 넘을 수 있다(시드가 32비트인 노드) | 뽑은 시드를 필드의 범위 안으로 접는다 |
| 하나도 끝나지 못한 배치도 준비한 그래프의 블롭을 남긴다. 출력을 가져오다 실패하면(디스크가 찼다) 이미 가져온 파일이 어느 기록에도 실리지 않고, 멈춘 뒤면 오류 코드가 `stopped`가 된다 | 그래프 블롭은 보고가 있는 배치만 남긴다. 가져오기의 실패는 그 실행의 `run_failed`이고 이미 가져온 파일은 그 실행의 출력으로 남는다 |
| 생성 프로바이더가 없는 동안에는 `gen.run`이 등록돼 있지 않아, 설정이 꺼져 있어도 에이전트가 생성 단계를 실행 취소·다시 실행할 수 있다 | 에이전트의 히스토리 이동은 지금 등록돼 있지 않은 연산의 단계도 넘지 못한다(그 연산의 규칙을 물을 수 없다) |

그대로 둔 것:

- 도구가 설정을 읽은 뒤 `run`이 잠금 안에서 다시 묻기 전에 사용자가 설정을 끄면, 에이전트는 제안이 아니라 거절(`agent_not_allowed`)을 받는다. 아무것도 실행되지 않는다.
- 하나도 끝나지 못한 배치에서 가져오기가 도중에 실패하면 이미 가져온 파일은 기록에 실리지 않은 채 저장소에 남는다(보류된 파일을 치우는 2-8에서 같이 본다).
- `gen.run`의 사전 조건은 프로젝트 잠금 안에서 프로바이더의 `validate`를 기다린다. 시간 제한은 프로바이더의 몫이다(카탈로그 계약).
