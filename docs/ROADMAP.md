## 첫 목표 — 한 줄기

**채팅에서 워크플로 하나를 local ComfyUI로 실행하고, 결과 이미지가 가운데 갤러리에 뜬다.**

네 계획이 따로 가다가 마지막에야 만나는 것을 막으려고 가장 먼저 잡는 목표다. 필요한 단계는 1-0, 1-1, 1-2, 1-3, 2-0, 2-1, 2-2, 2-3의 에셋·생성 최소분, 3-0, 3-2의 최소분, 4-0, 4-1, 4-2다. 각 단계에서 이 목표에 필요한 만큼만 먼저 만든다.

## 단계를 다루는 법

- 단계 하나가 브랜치 하나·PR 하나다(`AGENTS.md` "브랜치·커밋·병합").
- 단계를 시작할 때 **단계 계획 문서** `docs/PLAN_<단계>.md`(예: `docs/PLAN_2-1.md`)에 상세 계획과 설계 결정을 쓴다. 끝나면 `docs/archive/`로 옮기고 경로를 고친다.
- 끝낸 단계는 아래에서 `[x]`로 바꾸고 무엇을 어느 패키지에서 했는지 한 줄로 적는다. 남긴 일은 `[ ]`나 "후속"으로 적는다.
- 아래 단계 목록은 출발점이다. 단계를 시작할 때 범위를 사용자와 다시 맞춘다.
- 단계가 정해야 하는 "미정"(`docs/DECISIONS.md`)은 단계 계획 문서에 안을 쓰고 사용자가 확인한 뒤에 구현한다.

## 계획 1 — 기반

빈 저장소에서 "dsh + 우리 번들"이 뜨고, 고치고 빌드하고 확인하는 고리가 도는 상태를 만든다. 무엇을 dsh에 맡길지도 여기서 확정한다. 읽을 문서는 `docs/DSH.md`다.

- [x] **1-0 저장소 틀** — 루트에 pnpm 워크스페이스와 `@deepseek-ai/dsh` 0.2.2-rc.5 고정, `packages/bundle`(`@cs/bundle`, 행 하나), `packages/ui-shell`(`@cs/ui-shell`, 호스트 절반만 있는 빈 플러그인), `scripts/dsh.ts`(프로필 만들기·실행·합성 구성 찍기), TypeScript 6.0.3 기본 설정과 `typecheck`, oxlint + Prettier(2026-11-26). 상세는 `docs/archive/PLAN_1-0.md`.
  - 정한 것: 개발용 home은 본 체크아웃의 `.dsh-home` 하나이고 스크립트가 번들 링크를 지금 워크트리로 다시 건다. 린트는 oxlint, 포맷은 Prettier. TypeScript는 6.0.3(`docs/DECISIONS.md` "확정").
  - 확인한 것: `pnpm install` → `pnpm dsh:profile` → `pnpm dsh:start`로 dsh 웹이 뜨고 콘솔 오류가 0건이다. `pnpm -s dsh:config` 출력에 `# == @cs/bundle` 계층과 `cs-ui-shell` 행이 보인다.
  - 후속: 타입 기반 린트 규칙을 켤지(1-2), 무시된 설치 스크립트가 에이전트의 셸 도구에 주는 영향(1-3).
- [ ] **1-1 브라우저 절반과 브라우저 번들 빌드** — 1-0의 플러그인에 브라우저 절반을 더한다. 브라우저 번들 빌드 스크립트(dsh 로더 형식, 공유 모듈 열한 개는 external, 그 밖의 `@deepseek-ai/*` 값 import는 빌드에서 거절), 브라우저 쪽 타입 패키지(`docs/DSH.md` "타입을 얻는 패키지"), CSS를 싣는 방식.
  - 완료 기준: TSX로 쓴 React 컴포넌트를 슬롯 하나에 등록해 화면에 보이고 콘솔 오류가 0건이다. 브라우저 번들에 React가 들어 있지 않다. 슬롯 등록의 `inject`로 `ctx`의 값과 콜백을 React 컴포넌트에 넘기는 형태가 동작한다(시험 코드는 이 형태를 쓰지 않았다).
  - 주의: Astryx 시험 코드가 전혀 없는 브라우저 번들로 띄우는 것은 이 단계가 처음이다(`docs/DSH.md` "확인하지 못한 것").
  - 정할 것: 호스트 절반을 `.ts` 그대로 내보낼지 JavaScript로 빌드할지(링크된 `.ts`를 Node가 바로 읽는 것은 1-0에서 확인했다. `docs/DSH.md` "플러그인 패키지 하나의 모양"), 패키지별 `tsconfig`와 `typecheck`의 구성(지금은 루트 프로그램이 `scripts/`만 본다), oxlint의 `react` 플러그인.
- [ ] **1-2 시험 틀** — Vitest(단위), dsh를 실제로 띄우는 조합 시험, `lint`·`test` 명령. 조합 시험은 두 가지를 갖춘다: 브라우저로 화면을 보는 것(`docs/DSH.md` "띄워서 확인하는 법"), 그리고 호스트 쪽 서비스를 부르는 것. 호스트 쪽은 화면용 API가 없는 동안에도 돼야 하므로 방법을 여기서 정한다(후보: `--patch`로 얹는 시험용 플러그인이 서비스를 부르고 결과를 파일로 남긴다. 미확인).
  - 정할 것: 타입 기반 린트 규칙을 켤지(`oxlint-tsgolint`가 따로 필요하다. `docs/DECISIONS.md` "미정").
  - 완료 기준: 명령 하나로 "dsh 기동 → 우리 플러그인 로드 → 콘솔 오류 0"을 확인한다. 시험용 호스트 플러그인이 dsh의 서비스 하나를 불러 결과를 돌려준다. `AGENTS.md` "명령"을 채운다.
- [ ] **1-3 실제 모델로 채팅 확인** — 1-1의 플러그인에 `docs/DSH.md` "채팅을 우측 탭으로 옮기는 코드"를 시험용으로 넣고 모델 키를 설정한 뒤, 우측 탭의 채팅에서 메시지·추론·도구 호출이 그려지고 전송과 중지가 되는지 본다. 브라우저를 닫아도 턴이 끝까지 도는지도 본다. 기본 프리셋의 셸 도구가 도는지도 본다(pnpm이 `node-pty` 등의 설치 스크립트를 돌리지 않은 상태다. `docs/DSH.md` "함정"). 시험용 코드는 3-0에서 제대로 만든다.
  - 완료 기준: 결과를 `docs/DSH.md`에 반영한다. 안 되는 것이 있으면 화면 구조(`docs/ARCHITECTURE.md` "화면 구조")를 사용자와 다시 정한다.
- [ ] **1-4 기능 대응 확정** — `docs/LEGACY.md` 대응표의 "후보"와 "미정"을 사용자와 정한다. dsh에 맡기기로 한 항목은 실제로 써 본다(예약, MCP, 스킬, 웹 검색, 서브에이전트, 첨부). 에이전트 프리셋에 무엇을 넣을지도 여기서 정하고(셸·파일 도구를 줄지, 기본 제공 프리셋을 끌지. `docs/DSH.md` "에이전트 프리셋"), 정한 구성의 프리셋을 번들에 넣는다.
  - 완료 기준: 대응표에 "후보"가 남지 않는다. 옮길 기능의 순서가 정해진다. 우리 프리셋으로 만든 세션의 에이전트가 정한 도구만 가진다(띄워 확인).
- [ ] **1-5 접속·배포** — 리버스 프록시 뒤에서 dsh 웹을 띄우는 구성(`--public-url`, `--trusted-host`), 토큰 주소 로그인의 실제 흐름(재시작하면 토큰이 바뀌는지), 프록시 쪽 인증을 더할지.
  - 완료 기준: 다른 기기의 브라우저에서 접속해 채팅이 된다. 구성을 `docs/ARCHITECTURE.md` "접속과 배포"에 적는다.
- [ ] **1-6 UI 언어** — 우리 화면만 한국어로 둘지, dsh 기본 화면까지 한국어 언어 팩을 등록할지 정한다. `ctx.locale`의 언어 팩 등록을 시험한다. 그때까지는 `AGENTS.md`의 임시 규칙(문자열을 패키지마다 한 모듈에 모은다)을 따른다.
- [ ] **1-7 규칙 문서** — 코드가 생기며 정해진 규칙을 `docs/CONVENTIONS.md`로 쓴다(디렉터리 규칙, 플러그인 한 개의 모양, 브라우저 절반의 규칙).

## 계획 2 — 4계층(서버 쪽)

DreamVerse의 서버 쪽 구조를 가져온다. 다시 쓰지 않고 DreamVerse 코드(MIT)를 옮기는 데서 출발한다. 읽을 문서는 `docs/DREAMVERSE.md`와 `docs/ARCHITECTURE.md` "네 계층"·"두 계약"이다.

- [ ] **2-0 프로젝트 계층 이식** — DreamVerse `@dv/project`(4,612줄)와 그 테스트를 옮겨 dsh 0.2.2-rc.5에 맞춘다. 고칠 곳은 `docs/DREAMVERSE.md` "dsh 0.2.2-rc.5와의 차이"의 5건이다. 가져온 코드의 고지를 `THIRD_PARTY_NOTICES.md`에 적는다.
  - 정할 것(단계 계획 문서에 안을 쓰고 사용자가 확인): 기록 디렉터리 이름, 도구 접두사, 서비스 이름, 영상 전용 용어를 어디까지 걷어낼지, 새 프로젝트의 폴더를 어디에 만들지.
  - 완료 기준: 1-2의 호스트 쪽 조합 시험으로 프로젝트 만들기 → 시험용 연산 실행 → 기록 파일에 한 줄 → 상태에 반영 → 실행 취소와 다시 실행이 통과한다. dsh의 도구 레지스트리에 그 연산의 도구가 등록된다.
  - 주의: 타입 검사까지만 확인했다. 실행은 이 단계가 처음이다. 프리셋으로 만든 에이전트에게 연산 도구가 실제로 보이는지는 모델 키가 있어야 확인된다. 1-3이 끝나 있으면 여기서 확인하고, 아니면 미확인으로 적는다.
- [ ] **2-1 계약 ①: 카탈로그** — ComfyUI에 맞는 카탈로그 계약을 정한다. 답할 질문은 `docs/ARCHITECTURE.md` "카탈로그 계약"에 있다.
  - 산출물: `docs/PLAN_2-1.md`(설계 결정), 계약 타입 패키지, 가짜 생성 프로바이더로 도는 시험.
  - 사용자가 설계안을 확인한 뒤에 확정한다. **4-2가 이 단계를 기다린다.**
- [ ] **2-2 계약 ②: 화면용 API** — DreamVerse `@dv/api`(1,304줄)를 옮긴다: 상태 읽기, 연산 목록과 실행, 기록, 실행 취소·다시 실행, 프로젝트 관리, 이벤트 스트림.
  - 완료 기준: 브라우저에서 상태를 읽고 연산을 실행하면 이벤트가 온다. 경로와 응답 모양을 문서로 남긴다.
  - **3-2가 이 단계를 기다린다.**
- [ ] **2-3 기능 컴포넌트** — 기능 컴포넌트 하나는 상태 조각 + 리듀서 + 연산(= 에이전트 도구) + 에이전트가 읽는 설명이다. 제안하는 순서: 에셋(가져오기, 폴더, 태그, 검토 상태) → 워크플로(그래프 템플릿, 가져오기, 그래프 패치) → 생성(실행, 배치, 검토) → 캐릭터 → 그 밖. 범위와 순서는 1-4가 정한다. 첫 목표에 드는 에셋·생성 최소분은 1-4를 기다리지 않는다.
  - 기존 도구가 연산으로 옮겨 간다. 목록은 `docs/LEGACY.md` "에이전트 도구"에 있다.
  - 옮길 때 `docs/LEGACY.md` "유지할 도메인 규칙"을 지킨다.
- [ ] **2-4 작업 절차(스킬)** — 기능 컴포넌트의 도구를 부르는 순서를 스킬로 적는다. 기존 앱의 시스템 안내문과 프리셋이 출발점이다.
- [ ] **2-5 채팅 참조** — 채팅에서 가리킨 에셋과 첨부 이미지를 프로젝트의 id와 에셋으로 바꾼다(DreamVerse `@dv/chat-references`). `@` 메뉴에 우리 항목을 더하는 것은 확인하지 못했다.

## 계획 3 — 화면

DreamVerse처럼 기본 dsh 화면을 교체한다. Astryx 없이 React 18 컴포넌트, dsh 기본 부품, 직접 쓴 CSS로 그린다. 읽을 문서는 `docs/DSH.md` "화면 교체"·"그릴 재료"와 업스트림 `docs/subsystems/slots.md`다. 넷 중 가장 크다(DreamVerse 화면 코드 약 21,000줄, 기존 앱 화면의 `.tsx` 약 21,600줄).

- [ ] **3-0 셸** — 브랜드, 왼쪽 내비게이터(프로젝트 목록), 가운데 틀, 채팅을 우측 패널 탭으로, 슬롯이 없는 기본 요소 숨기기.
  - 정할 것(사용자 확인): 화면에 쓸 제품 이름과 마크(기존 앱 이름은 ComfyStudio다), 숨길 기본 요소의 목록(DreamVerse의 `packages/dv/ui-shell/src/client/chrome.tsx`가 출발점이다), 프로젝트 하나에 세션을 몇 개 둘지.
  - 완료 기준: 프로젝트를 만들고 열 수 있고, 우측 탭의 입력창에 글을 쓸 수 있다. 콘솔 오류 0건, 라이트·다크 모두 확인. 메시지가 오가는 것은 모델 키가 있어야 하므로 1-3의 결과를 따른다.
  - 출발점: `docs/DSH.md` "화면 교체"의 장치(슬롯 교체, 우측 탭, 채팅 재배치)는 띄워 확인했다. 다만 그 시험 코드는 `ctx`의 값을 모듈 변수로 React 컴포넌트에 넘겼다. 규칙대로 쓴 형태는 1-1에서 확인한다.
- [ ] **3-1 자체 부품** — dsh 기본 부품에 없는 것(표, 슬라이더, 셀렉트, 트리, 카드 등)을 만든다. 토큰·부품·사용 예를 이 저장소의 `docs/DESIGN.md`에 쓴다. 기존 앱의 `src/components/ui`(942줄)와 기존 저장소의 `comfy-studio/docs/DESIGN.md`가 참고다.
- [ ] **3-2 첫 화면: 갤러리** — 화면용 API에서 에셋을 읽어 그리고, 이벤트가 오면 다시 읽는다.
- [ ] **3-3 워크플로·생성·배치 검토** — 워크플로 목록, 실행 폼, 진행률, 배치 검토.
- [ ] **3-4 채팅 안의 카드** — 도구 결과와 제안(생성 제안, 그래프 패치 제안, 삭제 제안 등)을 카드로 그리고 승인·거절을 받는다. 실제 모델이 있어야 확인할 수 있다.
- [ ] **3-5 설정 화면** — ComfyUI 서버 등록·연결 테스트·모델 목록을 dsh 설정 화면의 슬롯에 넣는다.
- [ ] **3-6 그 밖의 화면** — 캐릭터, 프리셋, 히스토리(기록) 탭 등. 범위는 1-4가 정한다.

## 계획 4 — Comfy 연결

ComfyUI 서버와 말하는 부분이다. 기존 `comfy-studio`의 `src/lib/comfy`를 옮기는 데서 출발한다. 읽을 문서는 `docs/LEGACY.md` "ComfyUI 연동"이다.

- [ ] **4-0 연동 라이브러리 이식** — `src/lib/comfy`에서 `runner.ts`와 `input-image.ts`를 뺀 21개 파일(5,108줄)과 그 테스트 18개를 패키지로 옮긴다. 같이 옮길 보조 모듈은 `media/png-text.ts`, `presets/match.ts`, `storage/sigv4.ts`, `storage/keys.ts`(합쳐 263줄)다. 파일별 구분은 `docs/LEGACY.md` "옮길 수 있는 범위"에 있다.
  - 정할 것(사용자 확인): 기존 저장소는 비공개이고 이 저장소는 공개다. 옮기는 코드와 테스트 픽스처를 공개해도 되는지 확인한다(`docs/DECISIONS.md` "전제"). 픽스처에 실제 서버 주소·키·개인 데이터가 없는지 본다.
  - 완료 기준: 옮긴 테스트가 통과한다. 이 패키지는 dsh에 의존하지 않는다.
- [ ] **4-1 서버 등록과 자격 증명** — ComfyUI 서버 목록을 어디에 둘지 정하고, 키는 dsh 자격 증명 저장소에 둔다. 연결 테스트.
  - 완료 기준: 키가 설정 파일·기록·브라우저 응답에 평문으로 남지 않는다.
- [ ] **4-2 생성 프로바이더와 실행(local)** — 카탈로그에 등록하고, local ComfyUI로 제출 → 진행률 → 완료 판정 → 출력 수집 → 에셋 저장 → 취소를 한다. 기존 `runner.ts`(657줄)는 앱 서비스에 묶여 있으므로 프로젝트 계층에 맞춰 새로 쓴다. `input-image.ts`와 `runner` 테스트 두 개는 이 단계에서 다룬다.
  - 완료 기준: 가짜 ComfyUI 서버를 상대로 한 시험과 실제 local ComfyUI 한 번.
- [ ] **4-3 서버 종류 확장** — Comfy Cloud → RunPod Serverless → Modal 순.
- [ ] **4-4 서버 조회 기능** — 노드 카탈로그 검색, 준비 점검, 모델 계열, 서버 실행 기록에서 워크플로 가져오기.
